# N.I.A 营业 VN 设计

## 目标

把原型中的机械关键词解析替换为一次完整的营业事件：酒馆主 API 生成节目开场与一个核心现场问题，玩家通过既有 VN 选项或自定义输入提供解决方案，主 API 续写结果并审查额外粉丝加分。

## 交互闭环

1. N.I.A 原型将企划书、当前五日日程、本次营业、偶像资料和已有公开印象交给主前端。
2. 主前端以独立的 `nia_business` 事务调用主 API。第一轮只允许生成 VN 正文、一个核心问题和四个制作人行动选项。
3. 既有 VN 播放器显示剧情与立绘。剧情播放完后展示四个选项、自定义行动入口，不提供提前结算。
4. 玩家提交一次解决方案。主前端进行第二次主 API 调用，携带第一轮原文、核心问题、玩家行动与企划约束。
5. 第二轮返回 VN 收尾及 `NIA_BUSINESS_RESULT`。正文播放结束后才显示结算，并把结果转发回 N.I.A iframe。

## API 契约

第一轮使用 `<NIA_BUSINESS_OPENING>` JSON 包裹结构化数据：

- `story`：只含 `dialogue` / `narration` 的 VN 文本。
- `problem`：单个、具体、可由制作人介入的现场问题。
- `options`：恰好四个不同思路的制作人行动，不预判结果。
- `continuity`：供第二轮引用的简短事实列表。

第二轮使用 VN 正文加 `<NIA_BUSINESS_RESULT>` JSON：

- `problemSolved`：布尔值。
- `baseFans`：由前端预设，不接受模型篡改。
- `bonusFans`：0 至 1500，前端截断并取整。
- `pressureDelta`：0 至 20，前端截断并取整。
- `impressions`：最多四项观众印象。
- `bonusReasons`：最多三项，必须引用本次剧情中实际发生的证据。
- `summary`：本次营业对企划方向的推进。

额外加分按五项证据整体判断：解决现场问题、发挥偶像特质、符合本轮公开形象、形成传播高光、制作人与偶像有效配合。前端不再用关键词推断这些结果。

## 前端职责

- N.I.A iframe负责发起营业和显示最终结算。
- 主页面负责主 API 事务、VN状态、选项与自定义输入、重新生成和错误恢复。
- 酒馆宿主桥继续只负责转发既有 `sendPrompt` / `aiReplyCommitted` 消息。
- 所有回复必须同时匹配 `requestId`、`channelLeaseId` 和 `ownerKind=nia_business` 才能提交。

## 错误处理

- 第一轮格式无效：保留营业上下文，允许重新生成，不生成本地伪剧情。
- 第二轮格式无效：保留玩家行动与第一轮剧情，允许只重试第二轮。
- API错误或超时：显示既有 VN 恢复界面，不机械结算粉丝。
- iframe离开或重复点击：同一营业 `businessId` 只允许存在一个活动事务。

## 完成标准

- 一次营业只出现一个核心现场问题和一次玩家介入。
- 系统选项与自定义行动都能进入第二轮。
- 第二轮正文在原 VN 系统内播放，结束后才返回受限结算。
- 不再调用 `parseGuidance` 或 `resolveBusiness` 决定营业加分。
- 直接打开原型时明确提示需要从酒馆主页进入，不伪造 API 营业结果。
