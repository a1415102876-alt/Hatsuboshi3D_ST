# 宿主级可拖动游戏收放球设计

## 背景

当前持久游戏 launcher 使用全屏 shell 承载游戏 iframe，并在 shell 内提供“退出游戏”按钮。该按钮在真实 SillyTavern 中经过多次兼容修复后仍无法可靠响应点击。现有证据表明，继续调整 shell 内按钮的监听器或样式无法消除宿主页面、全屏层和 iframe 之间的点击层级风险。

本设计以宿主级可拖动悬浮球替换 shell 内退出按钮。悬浮球是 shell 的兄弟节点，始终位于 iframe 之上，通过隐藏和显示 shell 收放游戏，同时保留原 iframe 节点及其运行状态。

## 目标

- 用户首次启动游戏后出现一个可拖动的圆形控制器。
- 点击圆球可以收起或展开游戏。
- 收起游戏不删除、不重载、不重新设置 iframe `src`。
- 圆球在游戏展开和收起时都保持可见、可点击。
- 鼠标和触屏均可拖动，拖动不会误触发收放。
- 多个楼层入口和脚本重复加载不会创建重复控制器。
- 兼容并迁移当前 V1/V2 持久 launcher，尽量复用已有 iframe。

## 非目标

- 不修改 `app.js`、Harness、Prompt、结算、Recovery 或存档语义。
- 不修改 shujuku 数据库桥接。
- 不持久化悬浮球位置到 `localStorage` 或宿主存档。
- 不解决本地存储配额问题。
- 不保留 shell 内的普通“退出游戏”作为第二套控制路径。

## 已比较方案

### 宿主级常驻圆球

实现最简单，触屏可靠，但位置固定，可能遮挡游戏局部内容。

### 宿主级边缘标签

占用面积最小，但入口不够明显，展开与收起状态的可读性较弱。

### 宿主级可拖动圆球（采用）

允许用户避开关键游戏内容。代价是必须区分点击和拖动，并处理触屏、视口边界及窗口尺寸变化。用户已选择该方案。

## 结构

宿主页面只维护以下单例节点：

- `#hatsu-persistent-game-shell`：全屏游戏容器。
- `#hatsu-persistent-game-frame`：已有游戏 iframe。
- 新的宿主级悬浮球：直接挂在宿主 `body` 下，与 shell 为兄弟节点。

悬浮球的 `z-index` 必须高于 shell。shell 的显示状态不能影响悬浮球的显示状态。旧的 shell 内退出按钮在迁移时隐藏并解除有效控制职责。

控制器继续作为宿主 `window` 上的单例。新版控制器拥有 shell、iframe、悬浮球、当前可见状态、当前拖动状态和当前页面会话内的位置。重复加载脚本时复用该控制器或将旧控制器迁移到新版，不叠加事件监听器。

## 生命周期与数据流

### 首次启动

1. 楼层入口调用宿主 launcher。
2. launcher 查找或创建 shell 和 iframe。
3. launcher 查找或创建宿主级悬浮球。
4. 游戏 shell 展开，悬浮球显示。
5. iframe 只在首次创建时设置 `src`。

尚未启动过游戏时不显示悬浮球，楼层入口卡片仍是唯一启动入口。

### 收起与展开

- 未发生拖动的短点击切换 shell 可见状态。
- 收起只改变 shell 的显示属性，不删除 shell 或 iframe。
- 展开复用同一个 shell 和 iframe。
- 悬浮球图标、`title` 和 `aria-label` 随状态切换，分别表达“收起游戏”和“展开游戏”。

### 拖动

- 使用 Pointer Events 统一处理鼠标、触控笔和触屏。
- `pointerdown` 记录起点并捕获指针。
- 移动距离超过固定阈值后进入拖动状态。
- 拖动过程中更新悬浮球位置，并将位置限制在当前可视区域内。
- `pointerup` 结束拖动；本次手势一旦越过阈值，不执行收放切换。
- 短点击没有越过阈值时才切换 shell。
- 窗口尺寸变化后重新夹取位置，防止圆球停留在屏幕外。

悬浮球位置只保存在当前控制器内存中。页面刷新后恢复到右侧中部默认位置。

## 兼容与迁移

- 若当前 V2 控制器存在，升级其节点引用和行为，不重建已有 iframe。
- 若只存在 V1 控制器或旧持久 frame，优先把其 iframe 移入当前 shell 并复用。
- 若旧 shell 内退出按钮存在，将其隐藏，避免形成不可用或语义冲突的第二入口。
- 多个 launcher 楼层同时存在时，共享同一个宿主控制器。
- launcher 楼层被数据库刷新移除时，宿主级 shell、iframe 和悬浮球继续存在。
- 本地非宿主 fallback 维持当前行为，不创建宿主级悬浮球。

## 错误处理

- 找不到可写宿主文档时，沿用现有 fallback，不创建部分完成的宿主控制器。
- shell 或悬浮球被外部脚本移除后，下一次 launcher 调用可重新绑定或重建缺失节点，同时尽量保留仍存在的 iframe。
- iframe 加载失败不自动重设 `src`；错误仍由现有游戏加载路径处理，避免隐式刷新状态。
- 拖动过程中发生 `pointercancel` 时，清理拖动状态，不触发收放。

## 可访问性与视觉约束

- 圆球使用原生 `button`，提供可随状态变化的 `aria-label` 和 `title`。
- 控件尺寸至少 44 x 44 CSS 像素，适合触屏。
- 使用高对比度前景和背景，并提供清晰焦点样式。
- 不使用文字胶囊按钮；使用明确的展开/收起图标。
- 默认位置为右侧中部，并保留少量视口边距。

## 测试设计

专项自动测试至少覆盖：

1. 悬浮球是宿主 `body` 的直接子节点，而不是 shell 或 iframe 的子节点。
2. 悬浮球层级高于 shell，shell 隐藏时悬浮球仍可见。
3. 收起和展开复用同一个 iframe 节点，且不重新赋值 `src`。
4. 短点击切换状态，超过阈值的拖动不切换状态。
5. Pointer Events 的鼠标和触屏路径均可工作。
6. 拖动位置被限制在视口内，窗口变化后重新夹取。
7. 重复脚本加载和多个楼层入口只产生一个悬浮球。
8. 楼层入口被删除后，悬浮球和游戏 iframe 仍存在。
9. V1/V2 控制器迁移保留已有 iframe，并停用旧退出按钮。
10. 本地非宿主 fallback 不创建悬浮球。

验证命令包括 launcher 专项测试、`node --check dist/hatsu-launcher/message-entry.js`、`git diff --check` 和完整测试套件。

## 真实 SillyTavern 验收

1. 从楼层入口首次启动游戏，确认游戏与悬浮球同时出现。
2. 使用鼠标和触屏分别拖动悬浮球，确认不会误收起游戏。
3. 点击悬浮球收起游戏，确认聊天页面恢复且圆球仍存在。
4. 再次点击展开，确认游戏内部状态没有重置。
5. 触发数据库楼层刷新，确认宿主级圆球与游戏 iframe 不被移除。
6. 重复加载多个 launcher 楼层，确认只有一个圆球和一个游戏 iframe。
7. 调整窗口大小和移动端方向，确认圆球始终留在可视区域。

由于本地 SillyTavern 受 BasicAuth 保护，自动化环境不能代替用户完成真实宿主点击验收；实现完成后由用户按本清单验证。

## 成功标准

- 真实 SillyTavern 中无需依赖 shell 内退出按钮即可稳定收起和恢复游戏。
- 收放及拖动过程不重载 iframe，不丢失游戏页面状态。
- 宿主刷新楼层、重复渲染 launcher 或重复加载脚本时，不产生重复悬浮球和 iframe。
- 改动严格限制在 launcher 控制层与对应测试。
